# stair-core —— 温哥华核心筒疏散楼梯计算器（项目上下文）

本文件供 Claude Code 在新会话中直接接手。它记录了在 claude.ai 里完成的第一阶段（计算器）的所有关键决定、规范依据、几何约定和测试方法，以及第二阶段（平面图布置与行走距离判定）的需求与建议方案。**修改计算逻辑前请先读完"几何约定"和"必须保持的行为"两节。**

## 1. 项目现状

- `src/calculator/StairCoreTool.jsx`：单文件 React 组件（≈1 900 行，已在 claude.ai 中迭代十余轮并通过用户验收）。默认导出组件；同时命名导出 `compute`、`buildSolids`、`defaultFloors`、`doglegGeometry`、`USES` 供测试和后续模块使用。
- 运行：`npm install && npm run dev`。`npm run build:single` 生成可双击打开的单文件 `dist-single/stair-core-calculator.html`。`npm run test:calc` 跑回归测试（tests/calc.test.jsx）。
- 依赖：react 18、three **0.128.0**（代码按 r128 API 写，`OrbitControls` 不可用，已自写轨道控制；勿升级到会改动 `Geometry`/`BufferGeometry` 行为的版本）、Tailwind 3（只用了基础工具类）。
- 用户所在地：加拿大 BC 省 Richmond，项目面向温哥华市。界面语言为中文。

## 3. 计算逻辑（compute）

1. 逐层人数 → 需求宽度 wReq = 人数 × mm/人。
2. 本层需楼梯数 nReq = max(2, ceil(wReq / 单梯最大宽度))；首层默认直接出室外不计入（`includeL1` 可切换）。
3. 贯通：上层楼梯必须通到出口层，`c[L] = max(nReq[L..N])`；楼梯 k 服务 `c ≥ k` 的楼层；只服务下部的楼梯标"裙房梯"。
4. 每部楼梯宽度 = roundUp(max(各服务层 wReq/c[L], 表列最小), 取整步长)。
5. 踢面数 = ceil(层高/180)；跑数 = max(基本跑数[折返 2 / 剪刀 1], ceil(层高/3 700), ceil(踢面数/X))。**折返梯允许奇数跑**，奇数跑使上一层楼层平台换到对面端（`floorEnd` 交替）。
6. 踢面分配 `distribute` 均分；折返梯 >2 跑时 `fitLandingHeadroom` 调整使相邻两跑之和 × 踢面高 − 上方板厚 ≥2 050（末两跑上方用楼板厚，其余用梯段板厚 waist）；无解则警告"无论如何分配都不够"。
7. 门：`doorMin` = 端墙贴侧墙 → 门扇+JAMB(50)+300；端墙居中 → 门扇+750；侧墙 → 门扇+300。折返梯 Lf = max(W, doorMin)；若任一楼层平台落在右端则 Lm 也取 Lf。剪刀梯 Lend = max(min(W,1100), doorMin)，Lmid = min(W,1100)。
8. 梯间内净：折返 (2W + gap) × (Lf + flightRun + Lm)，flightRun 取所跨楼层最大；剪刀两梯共井 (Wa + 隔墙 + Wb) × (2·Lend + body)。分区（zones）按楼梯数变化处切分，给出并列布置的核心外包尺寸与面积。

## 4. 几何约定（平面、剖面、3D 三处共用，勿分别改）

- 坐标：x 沿梯间长（0 = 左端墙内侧），y 沿梯间宽（0 = band 0 侧墙内侧），z 竖向。
- **band**：折返梯两条梯段带。band 0 = y∈[0,W]，band 1 = y∈[innerW−W, innerW]。梯段带在整栋楼**连续交替**：`doglegGeometry` 里 `band0`（本层首跑所在带）= 上一层末跑带 + 1 mod 2，保证到达跑与起步跑永远在不同带。
- **end / floorEnd[L]**：本层楼层平台所在端，0 = 左，1 = 右；`fs = end===0 ? -1 : +1`；`xa` = 对面（中间/休息）平台边缘。
- 偶数跑 j（`toward`）从楼层平台一侧走向对面，终点 = `far[band]`；奇数跑从对面走回楼层平台一侧。
- **平台与楼板分两半**（以 y = innerW/2 为界），每半长度贴合各自带内的梯段：楼层平台 `floorEdge[band0] = 首跑起步 x`，`floorEdge[1−band0] = 上一层末跑到达 x`；休息平台 `halves` 同理。这是用户明确要求的（避免穿模/对不上边缘）。
- 平面图第二带显示的是**从下一层到达本层的那一跑**（可向下走），不是本层第二跑；首层无下层时显示本层第 2 跑。
- 剖面：band 0 为近侧（实线），band 1 虚线；楼板半边不同长时短的一半以虚线示意。
- 门：默认贴下行梯段一侧（`doorSide: "dn"`，下行带 = 1 − band0）的侧墙，铰链在侧墙侧，门闩朝中央；顶层用 `storeyGeo.top.arrive.band`。剪刀梯 A 梯贴 y=0 侧墙、B 梯贴 y=innerW 侧墙。
- 3D（`buildSolids` → `Stair3D`）：踏步为锯齿状盒体（每级向下延伸 waist），最后一级用 60 mm 薄片表示踢面；平台/楼板按两半；四面墙半透明；出口门橙色 2 100 高；每层楼层平台站一个 1.8 m 绿色 low-poly 小人（`figures`）。WebGL 不可用时显示提示而不崩溃。

## 5. 必须保持的行为（用户已验收）

- 左栏输入是**草稿**，点击"确认并计算"才复制为 `inp` 并重算；未确认时按钮变蓝、结果区顶部出现黄色提示。**左栏任何地方不得直接索引确认结果**（`res.perFloor[i]` 可能不存在——曾因此两次崩溃：`reading 'counted'`、`reading 'ol'`）。查看类选项（平面楼层、剖面起始层、3D 范围）不需确认。
- 默认值：层数 5；首层商业 800 m² 层高 **9 000** 板厚 300；L2 餐饮 4 200；L3–4 办公 3 800；L5 起住宅 700 m²、16 卧室、3 000；墙厚 300；单梯最大宽 1 500；每跑最多 **10** 级；踏面 280、踢面 ≤180、梯井 150、剪刀隔墙 200、门扇 950、门在端墙贴下行侧墙、梯段板厚 180、取整 50。
- 逐层核查表标注"级数上限 / 已按净高调整 / 平台换端"；条文表分四级来源；"出口门位置核查"表逐条给 ✓ / ✗ / △。
- 回归测试 `npm run test:calc` 覆盖：默认例子分跑、贯通规则、带交替与楼板边缘连续、3D 实体零重叠、门做法对平台深度的影响、单出口判定。改几何后必须通过。

## 7. 下一阶段：平面图上布置核心筒 + 行走距离判定

用户需求原文："我通过特定平面图，在上面摆放楼梯核心筒。你通过核心筒楼梯出口到走廊到平面图的某一点的距离来计算楼梯布局是否符合规范。"

**2026-09-21 进度（在没有 Node 环境的 Claude Desktop 会话里做的第一版，未跑 `test:calc`，请下次在有 Node 的环境里补跑）：**

- 用户对两个前置问题的回答：平面图格式——图片上传和手动坐标输入两种都要，可切换；走廊距离——手绘折线点击测距；校核范围——疏散距离(3.4.2.5)、两出口间距(3.4.2.3/DIST45)、核心筒越界与相互重叠，全部都要。
- **实现方式与本节建议架构不同**：由于是在 claude.ai 风格的单文件环境里直接迭代（用户先给的是导出的独立 `stair-core-calculator V1.jsx`），新功能直接加在了 `StairCoreTool.jsx` 内部（新增纯函数 `pointInPolygon/coreLocalToWorld/coreWorldToLocal/coreCorners/coreDoorWorld/polylineLength/polygonDiagonal/polysOverlap/travelLimit/requiredExitSeparation/clientToMm/rescalePositions`，新增组件 `CoreShape`/`DoorMarker`/`PlanEditor`，新增 state `plan`），**没有**按下面建议拆到 `src/plan/`。下次接手时请先问用户是否要重构成独立模块（要保证 `npm run test:calc` 全过、界面行为不变，重构本身就是一次风险操作）。
- 几何与坐标约定：平面布置模块的坐标一律以 mm 存储；核心筒本地坐标系原点在角点、x 沿长度、y 沿宽度，`rot` 为角度制绕原点旋转；有底图时通过"标定"（点两点+输入实际距离）得到 `mmPerPx`，无底图时 `naturalW/H` 直接是假定的平面 mm 范围、`mmPerPx=1`；SVG `viewBox` 直接用 mm，不再手动做像素换算。
- 出口间距（3.4.2.3）按"已绘制楼层边界的包络对角线"近似，不是精确的"楼层区域对角线"；两个出口的实际间距用各自核心筒的"门标记"（可拖动的黄点，默认在核心筒长边中点，用户可拖到实际门位置）算欧氏距离，不是路径距离。
- 疏散路径是**静态折线**：点击加点，或用"吸附终点"按钮把最后一点对齐到某个核心筒当前的门位置；之后再拖动核心筒/门，已画的路径端点**不会跟着动**，需要用户重新绘制或重新吸附。这是简化实现，不是自动路由（可行域/最短路径），如果用户后续要"自动画出到最近出口的最短路径"，需要按本节原建议做 `Routing`（可见图 Dijkstra 或栅格 BFS）。

**2026-09-21 第二轮进度：墙体 / 门 + 自动最短路径（对之前"路径是静态折线"这一简化的正式解法）：**

- 用户要求：默认给一个 50×50 m 的示例平面（环形走廊 + 核心筒），并且要能添加/删除/修改墙体和门来"制造走廊通道"，让工具自己算，而不是靠手动点折线。
- 新增数据：`plan.walls`（`{id,x1,y1,x2,y2,t}` 线段）、`plan.doors`（`{id,wallId,at,width}`，`at` 是沿墙从起点量起的距离）。可视化上墙体是粗线，门是墙上挖空的一段（渲染时在门的位置盖一段背景色线"抠掉"墙体，配合可拖动的白色墙端点方块和门位置圆点）。
- 新增纯函数：`wallLength/doorWorldOnWall/nearestWallPoint`（添加门时吸附最近的墙）、`buildObstacleGrid`（把边界+墙体+门的缺口+核心筒栅格化成一张 0/1 网格，格宽按 `clamp(min(mmW,mmH)/150, 200, 500)` 取，50×50 m 默认约 333 mm/格）、`dijkstraFromSource`（8 方向、禁止斜穿两个相邻格都被墙挡住的"对角线穿墙"、用二叉堆）、`computeAutoPath`（从任意点单源 Dijkstra 后，在各核心筒门所在格里取最近的，回溯路径、去掉共线点、首尾点换成精确的起点/门坐标再量长度）。
- 新增路径类型：`paths[].kind === "auto"`，只存 `src`（起点）与 `targetCore`（null=最近），`pts`/`length` 每次渲染时用 `useMemo` 现算——**这解决了第一轮里"移动核心筒或改路径后，已画路径不会跟着动"的问题**：自动路径类型下，移墙体/开关门/拖核心筒都会让路径实时重新寻路。手动折线类型（`kind:"manual"`）保留，仍是静态点。

**2026-09-29 第十轮：新增"按标注数字自动标定比例"——OCR 识别图纸上的尺寸标注（如"2400mm"），配对最近的线自动算出比例（`npm run test:calc`/`test:pdf`/`test:raster`/新增的 `test:dimension` 全过，并用真实文件 `Plans_V1.pdf` 做了端到端验证）：**

- 用户提的需求：想让工具自己读图纸上写的尺寸数字（比如"2400mm"）来定标定比例，不用再手动点两个点、手动输入已知距离。技术路线：用 `tesseract.js`（OCR，浏览器里跑，纯前端，不用后端，做法上跟 pdf.js/前几轮的图像边缘识别是同一套"能不能不加后端就搞定"的筛选标准）识别图纸上的文字，找出"看起来像尺寸标注"的数字，再给每个数字配上离它最近、长度说得通的一条线（复用上一轮栅格识别产出的原始线段——尺寸线本身也是图上的一条线，跟墙线用同一套线段提取逻辑，不用另外写一遍），算出"这个数字的毫米值 / 这条线的像素长度"当候选比例。
- 新增 `src/plan/dimensionDetect.js`（纯数组运算，不依赖 DOM/OCR，可在 Node 单测）：`parseDimensionValueMm(text)` 解析"2400"/"2400mm"/"2.4m"/"240cm"/"1,200"这类文字（没写单位按毫米算，是常见的公制图纸习惯），过滤掉太小（比如门编号、轴线号）或太大（比如总长/面积）的数字；`matchDimensionCandidates(words, segments)` 给每个数字文字找一条最近的、长度明显比文字本身大的线段当尺寸线，产出候选（不保证找对，只是候选，最终由用户点选确认）。
- `pdfWalls.js` 新增 `detectDimensionCandidates(pdfPage)`：`await import("tesseract.js")`（动态引入，跟 pdf.js 一样只在用户真点了这个功能才加载）→ `createWorker("eng").recognize(canvas)` 拿到文字+坐标 → 跟同一张背景图上跑一遍 `detectRasterSegments`（复用上一轮的栅格线段提取，不需要再识别成墙，只要原始线段）→ 丢给 `matchDimensionCandidates`。**这是目前工具里唯一一个需要联网的功能**——`tesseract.js` 默认从官方 CDN（`cdn.jsdelivr.net`）下载 worker 脚本、WASM 核心、语言包，没有内嵌到本地/单文件版本里（语言包有几 MB，内嵌会让 `build:single` 的单文件体积进一步膨胀，而且大多数场景用不上，不值得内嵌）。
- UI：`hasPdfPage` 时在"标定比例"按钮旁多一个"按标注数字自动标定比例"按钮；点了以后识别出来的候选叠加显示成紫色标记（圆点+文字+一条高亮显示的对应尺寸线），点其中一个就直接按它的比例生效（复用已有的 `rescalePositions`/`mmPerPx` 机制，跟手动标定比例是同一套后续逻辑），不需要用户自己再输一遍数字；`dimensionCandidates` 是组件内 state（不进 `plan`，标定一次就清空，不需要持久化）。
- **真实文件端到端验证时踩了一个新坑，值得记一下**：加了 `tesseract.js` 依赖后，Vite 第一次遇到这个新依赖会触发"依赖重新预打包 + 自动整页刷新"（控制台能看到 `✨ new dependencies optimized: tesseract.js` / `✨ optimized dependencies changed. reloading`），如果这个自动刷新恰好跟正在进行的 PDF 上传流程撞在一起，会导致 pdf.js 的 worker 陷入"发出请求但永远收不到回应"的假死状态（不报错，`loadPdfPage` 的 Promise 永远不 resolve/reject，UI 一直卡在"正在解析 PDF…"）——这不是代码逻辑的 bug（用同一份文件重启 dev server 之后立刻正常，`loadPdfPage` 从卡死变成 967ms 内完成），而是"新增一个大依赖后第一次触发的 Vite 预打包刷新，恰好跟一次异步操作撞在一起"这种时序巧合。**教训**：以后新增一个此前没装过的大依赖（尤其是会被动态 import 的）之后，第一次在浏览器里测试前，先重启一次 dev server（不要等它自己触发"预打包变化后自动刷新"），避免这种自动刷新跟正在进行的异步流程互相打架；如果测试时发现某个异步操作"没报错但一直不返回"，也要考虑到这个可能性，不要一上来就怀疑是自己刚写的代码逻辑错了。

- 实现（`rasterWallDetect.js` 新增两个函数）：
  - `labelOpenRegions(imageData)`：先对整张图二值化（大津法自动阈值，暗=墨迹，亮=空白纸面），再对"空白纸面"做经典的连通区域标号（并查集实现的两遍扫描算法），记录每个连通区域的像素面积。
  - `filterWallsByRoomAdjacency(walls, regions)`：对 `detectWallCandidates` 已经配对好的每一面墙候选（这时候知道了它的中心线和厚度），沿中心线在两侧各探一个点（探测距离按这面墙自己的厚度自适应——`wall.w/2 + 余量`，不用固定值，因为固定值要么探不穿粗墙、要么对薄墙探过头），如果两侧分别落在两个不同的"面积够大"的开放区域里，就认定这面墙真的分隔了空间，留下；两侧探到同一个区域（说明线两头绕一圈其实是连通的，没有真的挡住什么），就是噪点，丢弃。`pdfWalls.js` 的 `detectRasterWalls` 调用顺序改成：先配对出墙体候选 → 按房间分隔关系过滤 → 再套用户设的线宽范围（上一轮加的滑块还在，现在是"两道过滤"叠加，不是二选一）。
  - 顺带调整了 `pdfWallDetect.js` 的 `PAIR_MIN_GAP_PX`（两条细线配对成墙的最小间距）从 8 降到 5——原来的 8px 会把真实测出来约 6px 粗的窄墙直接挡在"能配对"的门槛之外，这是这次深入看真实数据之前没发现的一个参数问题。
- **踩过的两个实现坑**（都在写单元测试的过程中自己发现并修掉的，不是猜的）：
  1. `otsuThreshold` 复用到灰度图二值化时，如果图纸干净到灰度只有 0（墨迹）和 255（纸面）两个极值（合成测试图正好是这样），算出来的最优阈值可能精确等于 0，这时候用严格小于号 `<` 判断"是不是墨迹"会导致灰度恰好是 0 的纯黑像素反而判不成墨迹——二值化整个失效。改成 `<=`。
  2. 探测点"两侧不一样就算墙"这条规则一开始写得太宽松：如果一侧是有效房间、另一侧探到的是**实心色块内部的墨迹本身**（不是真的开放空间），也会被误判成"分隔了空间"——写单测时故意放了一个不挨墙的实心小方块（模拟结构柱），结果它的四条边全部被误收。改成只有"另一侧探到的是空白纸面、只是这块区域偏小"才放宽，探到的是墨迹本身一律不算。

**2026-09-29 第十八轮：矢量 PDF 路线——柱子不再被识别成两面墙；证实"斜线变横平竖直"不是矢量路线的问题（`npm run test:pdf` 扩充后全过，`test:raster`/`test:room`/`test:calc` 全过；浏览器里用合成矢量 PDF 走通真实上传→识别链路）：**

- **问题②的根源**：柱子的四条边两两平行、间距又落在配对范围内，`pairParallelSegments` 天然会把它们配成两面互相垂直的短"墙"。修法（`pdfWallDetect.js`）：
  - `extractStrokedSegments` 给每条线段打上 `pathId`/`sub`（属于哪条路径的哪条子路径）和 `closed` 标记（遇到 `h` 指令、或最后一个 `l` 画回起点）。pdf.js 会把 `re`（矩形）指令展开成 m/l/l/l/h，所以 CAD 里用矩形画的柱子能靠这个标记直接认出来。
  - 新增 `findColumnBoxes(segments)`：两种情况认成柱子——(a) 闭合四边形，相邻边垂直、对边平行、边长 ≤120px、长宽比 ≤2.5；(b) 没闭合、四条边各自单独描的：两条平行线几乎完全重叠（≥80%）、各自长度都 ≤2.5×间距、也都 ≤120px。柱子的边整个从待配对线段里拿掉，`detectWallCandidates` 默认先跑这一步（`opts.excludeColumns=false` 可关）。返回的 `columns`（中心/尺寸/角度）目前没在 UI 上显示，留着以后可以画成柱子标记。
